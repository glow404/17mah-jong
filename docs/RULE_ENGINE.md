# 规则引擎设计

## 边界与模块

`lib/rules` 是纯 TypeScript 规则核心：不导入 React、Next/Vinext、数据库、HTTP 或浏览器 API。传入数组不会被规则函数修改；随机性只通过 `RandomSource` 参数进入。应用端按职责导入模块，`lib/mahjong.ts` 保留为兼容性 barrel，供旧调用方逐步迁移。

| 模块                       | 职责                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| `tiles.ts`                 | 0–33 牌种、0–135 实体牌转换，牌面标签，排序、宝牌循环、洗牌和种子随机源 |
| `hand.ts`                  | 34 种计数、标准牌型拆解、七对子/国士判断、和牌判断和听牌枚举            |
| `scoring.ts`               | 役种、番符、满贯倍率、最高拆解计分和听牌说明                            |
| `furiten.ts`               | 临时振听和自舍牌导致的永久振听判定                                      |
| `selection.ts`             | 从实体牌池启发式搜索 13 张听牌手牌                                      |
| `errors.ts`                | 严格输入/状态 API 共用的错误类型和编号校验                              |
| `types.ts`                 | 规则内部的牌和随机源类型；稳定共享类型从 contracts 导入                 |
| `lib/contracts/mahjong.ts` | 客户端与 API 共用的计分、座位、结算和脱敏房间快照类型                   |

## 算法与复杂度

- 牌种映射：实体编号整除 4 得到牌种，时间 `O(1)`；牌墙用 Fisher–Yates 洗牌，时间 `O(136)`、额外空间 `O(136)`。
- 可复现随机：`createSeededRandom(seed)` 返回 Mulberry32 随机源；`createWall(random)` / `shuffle(items, random)` 必须显式接收该依赖。相同整数种子和调用序列产生相同结果；规则模块内没有隐式全局随机调用，应用层可显式注入 `Math.random`。
- 标准拆解：依次尝试 34 种对子，递归取剩余牌中最小牌并尝试刻子/同花色顺子；每层至少消费 3 张，最多四层。每个候选分支最多二叉，因此 14 张手牌约为 `O(34 × 2⁴)`，辅助空间 `O(34)`，另加输出拆解空间。
- 七对子、国士：一次 34 槽计数，时间 `O(14 + 34)`，空间 `O(34)`。
- 听牌枚举：遍历至多 34 个候选牌种，逐个执行和牌判定；当前实现上界约 `O(34 × 34 × 2⁴)`，空间由拆解结果决定。
- 计分：对每一个合法标准拆解扫描手牌和固定牌种范围；时间 `O(D × (14 + 34))`，其中 `D` 是对子尝试与至多四层二叉递归形成的拆解分支数。计分会比较所有拆解并选倍率、番数、符最高的结果。
- 听牌推荐：枚举受限的三面子 + 雀头 + 搭子候选并实际验证听牌。全局最多对 5,200 个不同候选作完整评估；这是启发式而非完整性保证。递归构造仍可能检查未计入该预算的重复组合，后续可按 profiling 结果增加节点预算或动态规划。

## 类型与非法输入

- `RuleEngineError` 提供稳定 `code`，目前严格校验 API 使用 `INVALID_TILE`、`INVALID_PHYSICAL_TILE`、`INVALID_RANDOM_VALUE`、`INVALID_SEED` 和 `INVALID_STATE`。业务分支应读取 `code`，不要依赖错误文案。
- `tileType`、牌面/宝牌转换、洗牌随机源和推荐池等严格入口会对越界值抛出 `RuleEngineError`。
- 对“判定问题”采取无效即不成立：`isWinningHand` 返回 `false`，`decomposeHand` / `waitTypes` 返回空数组，`evaluateWin` 对无效手牌结构返回 `null`。这样来自客户端的手牌不能被判成合法牌型；API 层仍应使用请求 Schema 给用户可理解的 4xx 错误。
- `assertTileType` 和 `assertPhysicalTileId` 可用于边界处将不可信数字转成经验证的牌编号；其 TypeScript 类型目前以 `number` 兼容现有 UI/API，运行时边界校验是必要的。

## 共享契约与包边界评估

`lib/contracts` 仅承载跨端 DTO 和计分结果等共享结构；房间内部状态、令牌和对手手牌不属于公开快照。API 的 `publicRoom` 返回值明确标注为 `RoomSnapshot`，以编译期检查防止字段形状漂移。

目前不值得额外拆成 npm/workspace 包：应用只有一个消费者，仓库保持单包私有，规则代码不依赖运行时框架，且 `lib/rules` 已形成可复制/测试的依赖边界。独立包会新增版本、构建产物、发布权限、变更日志和兼容性承诺，但暂时没有第二个项目或外部用户获益。若规则引擎要被第二个应用复用，或决定公开发布规则包，再抽为 workspace package；此时应以 `lib/contracts` 的 DTO 和纯函数 API 为迁移边界，并配置 package exports、类型声明、独立版本和兼容性策略。

## 当前规则模型说明

本引擎服务本项目的二人自定义玩法，不宣称完整实现雀魂/标准日麻：无副露/自摸/立直声明流程，固定两立直与东/西自风；必须满贯起胡；只接受荣和；对局底分直接乘档位；役满按单一 4 倍处理。普通型符数使用项目当前简化算法（固定 30 符底，加对子/刻子/等待符并向上取整），不是标准日麻完整符计算。改变这些约定前请同步更新 `docs/RULE_COMPATIBILITY.md` 和规则矩阵测试。
